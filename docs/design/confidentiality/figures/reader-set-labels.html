The frame: objects, holders, sinks

Objects (data) on the left, holders in the middle, and sinks on the right. A holder is whoever holds raw bytes: the agent's session, one tool call's process tree, a long-lived process. A sink is where bytes can go that Mandu can see: a model (a declared endpoint), a destination (a host, a socket, a synced folder), storage (any other file), the human. Mandu acts at three gates: when a program opens an object, when a holder sends to a sink, and when it writes a file.

Programs are not sinks. A program is an opener: it is checked at the read gate against the file's reader list, and nowhere else. The label that travels with the data names sinks only. The OS layer cannot back more: once bytes are inside a tool call's process tree, it cannot tell which program holds them (in python3 … | tee, tee holds the data and is no reader). Plan 13's §4 is this frame written as a lattice. Six refinements keep the frame faithful to what Mandu actually does:

  1. Files are on both sides. A write is a sink, and the written file becomes an object again, referring to the labels of the data its writer held. A label that is wrong at the write is wrong at every later read. Today it is wrong in two ways. A derived file is served raw to every program: the guard's index loads once and never learns derived paths, and mv drops the label (D4). A file opened before the read gets no label at all (D5).
  2. The user is on both sides too. Prompts are objects. The human terminal is a sink that always sees originals (the reply filter). Today a prompt is public without condition: user-role text is forwarded raw, so a pasted key reaches the provider. Plan 13 §4.8 records the decision to scan prompts for the values of registered secrets and replace each with its symbol. The scan for secret shapes is withdrawn, after Plan 14 §1 rejected masking by shape (Figure 6).
  3. The agent is not an ordinary program. Its process only ever gets the twin, and what it reads goes straight into its model's context. For the agent, read and send to the model are one event at one chokepoint, the model-API proxy. Its holder is the session, and the session's label is the watermark. That is why the level (which models may see the data) is the column that separates the four levels.
  4. Holders carry labels, and data moves between processes. A holder that reads a secret raw keeps a label that only shrinks, and passes data on through pipes and sockets. A check made only at the open (access control) cannot see A | B or a holder that read two files. The label must travel with the holder: this is information-flow control, not access control alone. That fourth arrow, process to process, is where the defects D1 and D2 live. Plan 13 approximates it by treating one tool call's process tree as one holder, which needs the tree recorded at fork and exec (D7).
  5. The outcome is not allow or deny. Each gate has four outcomes: raw symbol / twin ask hard deny. The symbol is the dual view: the holder keeps working on data it cannot see. An approval defaults to once: an Inbox row offers Deny, Allow once, Allow this session and Always, and only Always writes to the policy.
  6. An object is data, not a path. The same bytes live under other names: .git/objects, copies, caches. git show HEAD:.env never opens .env. The launcher's git object-store twins (confidentiality.md §7.2a) cover one such name; every other name needs a label of its own.
